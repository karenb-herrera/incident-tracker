# Incident Tracker tool

A simple Incident Tracker REST API built with Java and Spring Boot. The application allows creating, viewing, filtering, updating, and deleting incidents.

A minimal JavaScript frontend is also included to demonstrate the API functionality.

## Tech Stack

* Java
* Spring Boot
* Spring Data JPA
* Hibernate
* PostgreSQL
* Maven
* JUnit
* MockMvc
* HTML / JavaScript

## Features

* Create incidents
* View all incidents
* Filter incidents by status and/or severity
* View an individual incident by ID
* Patch an incident's status
* Delete an incident
* Request validation
* Separate test database
* Automated integration-style API tests
* Minimal frontend for interacting with the API

## Architecture

The application uses a layered architecture:

```text
HTML + JavaScript
   ↓
Controller
   ↓
Request DTO + Validation
   ↓
Service
   ↓
Entity
   ↓
Repository
   ↓
Hibernate / JPA
   ↓
PostgreSQL
```

### Controller

The controller handles HTTP requests and responses.

It is responsible for:

* Mapping API endpoints
* Receiving request data
* Request validation
* Returning appropriate HTTP status codes

### Service

The service contains the application's business logic.

For example:

* Setting a new incident's status to `OPEN` as default
* Checking whether an incident exists before updating or deleting it
* Applying the requested filters

### Repository

The repository handles database access through Spring Data JPA.

`IncidentRepository` extends `JpaRepository`, which provides standard CRUD operations.

A custom query is used for filtering incidents by status and severity.

### DTOs

The application uses Data Transfer Objects (DTOs) to define the structure of incoming API requests separately from the database entity.

IncidentCreateRequestDto contains the fields clients are allowed to provide when creating an incident, while IncidentPatchRequestDto contains the fields allowed when updating an incident.

DTOs also provide a place for request validation using annotations such as @NotBlank and @NotNull.

This prevents clients from directly controlling fields such as id, timestamp, or the default status when creating an incident.

### Entity

`Incident` represents the database entity and maps to the PostgreSQL `incidents` table using JPA annotations.

### Hibernate / JPA

JPA provides the persistence API between the Java application and the database.

Hibernate is the JPA implementation used by Spring Boot. It handles mapping the Java `Incident` entity to the PostgreSQL table and translates repository operations into SQL.

## API Endpoints

### Create an Incident

```text
POST /incidents
```

Request:

```json
{
  "title": "Server down",
  "description": "Production server is unavailable",
  "reported_by": "Alice",
  "severity": "HIGH"
}
```

Returns `201 Created`.

The timestamp is generated by PostgreSQL and the status defaults to `OPEN`.

### Get All Incidents

```text
GET /incidents
```

Returns a list of all incidents.

Optional filters:

```text
GET /incidents?status=OPEN
GET /incidents?severity=HIGH
GET /incidents?status=OPEN&severity=HIGH
```

### Get an Incident by ID

```text
GET /incidents/{id}
```

Returns the requested incident or `404 Not Found` if the ID does not exist.

This endpoint was added as a small extension to make individual incident retrieval available in addition to the required list endpoint.

### Update Incident Status

```text
PATCH /incidents/{id}
```

Request:

```json
{
  "status": "IN_PROGRESS"
}
```

Allowed status values:

* `OPEN`
* `IN_PROGRESS`
* `RESOLVED`

Returns `200 OK` when successful or `404 Not Found` when the incident does not exist.

### Delete an Incident

```text
DELETE /incidents/{id}
```

Returns `204 No Content` when the incident is successfully deleted.

Returns `404 Not Found` if the incident does not exist.

## Database

PostgreSQL is used as the persistent relational database.

The application uses two databases:

```text
incident_tracker
incident_tracker_test
```

The production/application database contains the `incidents` table.

The test database is isolated from the application data so automated tests do not modify real application data.

The main application uses:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

This allows Hibernate to validate that the database schema matches the entity mappings without automatically modifying the schema.

The test database uses:

```properties
spring.jpa.hibernate.ddl-auto=create-drop
```

This allows the test schema to be created when the test context starts and removed afterward.

### Database Schema

The `incidents` table contains:

| Column      | Type                     | Description                           |
| ----------- | ------------------------ | ------------------------------------- |
| id          | bigint                   | Auto-generated primary key            |
| title       | varchar(255)             | Required incident title               |
| description | varchar(255)             | Incident description                  |
| reported_by | varchar(255)             | Person who reported the incident      |
| severity    | varchar(20)              | LOW, MEDIUM, or HIGH                  |
| timestamp   | timestamp with time zone | Database-generated creation timestamp |
| status      | varchar(20)              | OPEN, IN_PROGRESS, or RESOLVED        |

The primary key is indexed by PostgreSQL.

## Configuration

Database credentials are provided through an environment variable.

Example:

```properties
spring.datasource.password=${DB_PASSWORD}
```

Set the environment variable before running the application.

On Windows PowerShell:

```powershell
$env:DB_PASSWORD="your_password"
```

## Running the Application

From the project directory:

```powershell
mvn spring-boot:run
```

The API runs on:

```text
http://localhost:8080
```

The frontend can then be accessed through the application.

## Running Tests

The test suite uses JUnit and Spring's MockMvc.

Run all tests with:

```powershell
mvn test
```

The tests use the separate `incident_tracker_test` database.

The test suite verifies:

* Successful incident creation
* Required-field validation
* Invalid severity validation
* Retrieving all incidents
* Filtering incidents
* Retrieving an incident by ID
* Handling an invalid incident ID
* Patching incident status
* Handling an invalid ID during PATCH
* Handling an invalid status during PATCH
* Deleting an incident
* Handling an invalid ID during DELETE
* Successful Spring application context startup

Each test starts with a clean set of incident data.

## Frontend

A minimal HTML/JavaScript frontend is included to demonstrate the API functionality.

The frontend is located at: src/main/resources/static/index.html

Spring Boot automatically serves files placed in the static directory. After starting the application, the frontend can be accessed at: http://localhost:8080/

The JavaScript is embedded directly in index.html; no separate JavaScript file or frontend framework is used.

The frontend uses the browser's fetch() API to communicate with the Spring Boot REST endpoints.

It supports:

* Creating incidents
* Viewing all incidents
* Filtering by status
* Filtering by severity
* Retrieving an incident by ID
* Updating incident status
* Deleting incidents

The frontend is intentionally minimal because the primary purpose of the assignment is the REST API. It provides a simple way to demonstrate the API functionality without adding unnecessary frontend complexity.

## Project Scope

The implementation intentionally remains small and focused on the requirements of the take-home assignment. Production-oriented features such as authentication, pagination, and advanced monitoring were considered as future improvements rather than implemented unnecessarily for the scope of the exercise.
